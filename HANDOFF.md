# Handoff: «Пульс» — трекер задач для команды

Next.js 16 (App Router, Turbopack) + Tailwind v4 + TypeScript. Деплой на Vercel,
БД — Postgres на Supabase (или in-memory без БД). Прод: team-task-tracker-delta.vercel.app.

## Что уже сделано

**Авторизация**: email+пароль (bcrypt), сессия — подписанная HMAC-кука
(`SESSION_SECRET`). Регистрация только по списку разрешённых email
(`allowed_emails`), первый зарегистрированный — автоматически admin.
Смена пароля пользователем, сброс пароля админом, удаление аккаунта
(с защитой от удаления себя/последнего админа/владельцев досок-пространств).

**Пространства (workspaces)** — мультитенантность: у каждой команды свои
доски, задачи, вопросы. Маршрутизация **по пути**, не по query-параметру:
`/w/[workspaceId]/boards`, `/w/[workspaceId]/questions`,
`/w/[workspaceId]/game`. Легаси `/boards`, `/questions`, `/game` —
редиректоры на актуальное пространство (cookie `ttt_current_ws` хранит
последний выбор). Приглашение по email работает даже для ещё не
зарегистрированных (`workspace_invites`, применяется при регистрации).

**Админ-панель** (`/admin`): разрешённые email, пространства и их участники,
роли/блокировка/сброс пароля/удаление пользователей.

**Доски и задачи**: канбан (4 этапа), приоритеты low/medium/high/**urgent**
(«Горящая» — визуально выделена, всегда сортируется первой). Вид задачи
«Обычная/Хаммеры/Суперхиты» с таргетом/фактом для акционных. Дедлайн с
датой и временем, просрочка подсвечивается. Сортировка: горящие → по
сроку → по приоритету. Поле «Комментарий исполнителя» редактирует
только назначенный исполнитель (проверено на сервере), «Описание» пишет
создатель. Ссылки в «Описании» и в «Комментарии исполнителя» рендерятся
кликабельными (`lib/linkify.tsx`, регэксп на http(s)/www, без сторонних
библиотек). Задача: экран просмотра (read-only) отдельно от редактирования
(доступно только создателю, `task.createdBy`). Поле «Найдено, шт.»
(Хаммеры/Суперхиты) редактируется исполнителем прямо в режиме просмотра
(быстрое поле рядом с прогресс-баром, сохраняется вместе с этапом/
комментарием), таргет не обязателен — если не задан, просто нет
знаменателя. Серверная проверка прав на `foundCount`: менять может
исполнитель или создатель (в `PATCH /api/tasks/[id]`). Диалог «Мои
задачи» (кросс-доска, с пометкой доски) — клик по задаче в диалоге ведёт
на `/w/[workspaceId]/my-tasks?taskId=...`. Тумблер «Только мои задачи» на
доске (`kanban-board.tsx`) убран по прямому запросу — своя подборка задач
и так есть отдельным разделом «Мои задачи» (`my-tasks-board.tsx`),
дублировать личный фильтр внутри самой доски не стали.

**«Мои задачи» — сводная доска** (`/w/[workspaceId]/my-tasks`,
`components/my-tasks-board.tsx`): канбан из задач пользователя со **всех**
досок пространства (`listMyTasksInWorkspace`, `/api/tasks/mine`), с тем же
drag-and-drop и `TaskDialog`, что на обычной доске. Отдельного хранилища
нет — редактирование/перетаскивание бьёт в тот же `PATCH /api/tasks/[id]`,
поэтому изменения сразу видны и на исходной доске (через её собственный
polling), и наоборот. Карточка задачи показывает бейдж с названием доски
(`TaskCard.boardName`). Создание новых задач здесь не предусмотрено —
только просмотр/редактирование существующих (неочевидно, в какую доску
класть новую).

Сайдбар «Просрочено/Сегодня» (переиспользуется и на обычной доске, и в
сводной). Индикатор непросмотренных задач (localStorage). Фоновый polling
раз в 12 сек (пауза при открытом диалоге/драге) — на обеих досках.

**Шапка (`components/team-header.tsx`)**: вкладка «Мои задачи» в
`NAV_LINKS` между «Задачи» и «Вопросы» (легаси-редирект `/my-tasks` по
образцу `/boards`/`/questions`). На вкладках «Мои задачи» и «Вопросы» —
бейдж-точка, если есть что-то новое «для меня» с прошлого визита: шапка
дёргает `/api/tasks/mine` и `/api/questions` для текущего пространства,
берёт максимум `updatedAt` и сравнивает с `localStorage`-ключами
`ttt_last_seen_my_tasks_${workspaceId}` / `ttt_last_seen_questions_${workspaceId}`
(проставляются самими страницами при просмотре — `my-tasks-board.tsx`,
`questions-list.tsx` — по аналогии с уже существующей меткой
`ttt_last_seen_${boardId}` на обычной доске). Кнопка «+» добавления
задачи в колонке и ссылка «Все доски» (выход с доски) сделаны заметнее
(цветной фон вместо едва видимой иконки/бледного текста).

**Скриншоты к задачам**: до 5 файлов-изображений на задачу, до 5 МБ
каждый (лимиты enforced в API, не в схеме). Прикреплять/удалять может
и создатель, и исполнитель задачи (`canManageAttachments` в
`app/api/tasks/[id]/attachments/route.ts`), удалить может ещё и тот, кто
сам загрузил файл. Хранится как base64 прямо в Postgres — таблица
`task_attachments` (без отдельного файлового хранилища/Vercel
Blob/Supabase Storage, сознательный выбор ради простоты при небольшом
объёме; см. «Важные решения»). Загрузка — через кнопку «Прикрепить»
(input type=file) или вставкой из буфера обмена (Ctrl+V) прямо в
диалоге задачи. Раздача файла — `GET /api/tasks/[id]/attachments/[attachmentId]`,
отдаёт сырые байты с правильным `Content-Type` (используется как `src`
у `<img>`), список метаданных — отдельным `GET .../attachments`.

**Вопросы** (`/w/.../questions`): приватная переписка 1:N, получатели —
только участники того же пространства (проверка на сервере).

**Мои заметки** (`/notes`): личные, не привязаны к пространству, папки,
автосохранение. Доступ строго по владельцу (проверено на сервере, 404 для чужих).

**Ссылки** (`/w/[workspaceId]/links`, `components/quick-links.tsx`; легаси
`/links` — редиректор по тому же образцу, что `/boards`/`/my-tasks`):
вкладка «Ссылки» в шапке (после «Мои заметки», иконка `Link2`) — раньше
здесь была попытка встроить сторонний сервис `https://promo.uzum.marketing`
(нет доступа к его коду, только URL + отдельный логин там) через `<iframe>`,
но сервис оказался запрещён для встраивания (`X-Frame-Options` — в браузере
буквально «refused to connect»), поэтому от iframe отказались. Сначала
сделали как страницу-«лончер» с хардкодным массивом `LINKS`, но выяснилось,
что нужны полноценные добавление/удаление и поиск — теперь это настоящая
персистентная сущность, общая для всех участников пространства (не
привязана к автору): модель `WorkLink` (`lib/models.ts`), CRUD в
`store-memory.ts`/`store-db.ts` (`createWorkLink`/`listWorkLinks`/
`getWorkLink`/`deleteWorkLink`), таблица `work_links` в `schema.sql.ts`
(`workspace_id`, `title`, `url`, `description`, `created_by` — прогнать
`npm run db:migrate`), роуты `GET/POST /api/links` и
`DELETE /api/links/[id]`, валидация `createWorkLinkSchema` в
`lib/validation.ts` (URL проверяется через `new URL()` + разрешены только
`http(s)`). Добавить может любой участник пространства (`CreateLinkDialog`
— диалог по образцу `CreateQuestionDialog`), удалить — тоже любой участник
(ссылки общие, не «свои» — проверка только `canAccessWorkspace`, не
`createdBy`), с подтверждением через `toast` (по образцу удаления доски в
`board-header-actions.tsx`, без `window.confirm`). Список — компактные
строки `panel divide-y` (по образцу `questions-list.tsx`), а не крупные
плитки: иконка-кружок, название, домен+описание одной строкой, при наведении
— кнопки «открыть»/«удалить». Строка поиска фильтрует по названию, домену/URL
и описанию на клиенте (не по API — список ссылок в пространстве небольшой).

**Мини-игры** (`/w/.../game`): клик по баннеру (`boards-banner.tsx`) ведёт
на экран выбора игры — `components/game-picker.tsx` (клиентский стейт
`selected: "samurai" | "dino" | null`; при `null` — две карточки-кнопки +
ссылка «← Все доски»). Обе игры принимают проп `onExit: () => void`,
который у `GamePicker` просто сбрасывает `selected` обратно в `null`
(возврат в меню выбора, а не уход со страницы).

- *Разрезание задач* (`components/samurai-game.tsx`, fruit-ninja-стиль):
  фон — копия главного экрана (шапка/баннер/кнопки, без досок), карточки
  летают в размере настоящих, с реальными названиями досок (тянутся через
  `/api/boards?workspaceId=...`). Пауза/рестарт/завершение раунда (`X` —
  не выход, только конец раунда) и отдельная кнопка «Выйти» (`LogOut`, и в
  панели во время игры, и на стартовом/финальном экране). Спавн карточек
  (`spawnObject`): `vx` вычисляется так, чтобы пик параболы (верхняя точка,
  где удобнее резать) приходился на случайную точку в средних 30–70%
  ширины арены, а не оставался у края экрана, как раньше.
  - **Наплывы карточек вместо линейного спавна, зелёная рамка отпуска,
    жизни вместо таймера** (жалоба: «задачи по две-три вылетали с разных
    сторон но не линейно... наплыв до 5», «отпуск должен подсвечиваться
    зелёной рамкой», «убрать ограничение по времени — игра останавливается
    если порезаны 3 отпуска»):
    - `pickBurstSize()` — раньше `step()` каждый раз спавнил ровно один
      объект (`spawnObject()`) через равный случайный интервал; теперь при
      срабатывании таймера спавнится «наплыв» — 1 (25%) / 2 (30%) / 3
      (25%) / 4 (13%) / 5 (7%) карточек подряд, пауза до следующего
      наплыва растёт вместе с его размером (`55 + burstSize*16 + rand*55`
      кадров), чтобы после пятёрки не заваливало сразу следующей волной.
      Сторона (`fromLeft`) и раньше выбиралась случайно на каждый объект
      независимо — внутри одного наплыва они и так могли не совпадать,
      но раньше это было незаметно, т.к. объекты появлялись по одному.
    - `spawnObject()`: `heightFactor` (высота дуги) и `targetX` (куда
      целится верхняя точка параболы) теперь случайны в диапазоне
      (`0.58–0.88` и `32–68%` ширины арены соответственно), а не
      фиксированы — иначе все карточки одного наплыва летели по
      идентичным синхронным дугам в одну точку и выглядели как один
      бросок с задержкой, а не как настоящий наплыв.
    - Карточка «Отпуск» получила заметную рамку (`border-[3px]
      border-[var(--color-stage-done)]` + внешний `box-shadow` того же
      зелёного цвета, `shadow-[0_0_0_4px_var(--color-stage-done-soft),...]`)
      — раньше был только тонкий 1px бордер от `.panel`, почти незаметный
      на скорости.
    - Таймер раунда (`ROUND_SECONDS`, `timeLeft`, `setInterval` на секунду)
      убран целиком. Вместо него — «жизни»: `MAX_VACATION_SLICES = 3`,
      `vacationSlicesRef`/`vacationSlices` считают порезанные отпуска в
      `sliceObject()`; при достижении лимита `sliceObject()` сам вызывает
      `finishGame()` (раунд теперь может идти сколько угодно, пока игрок
      не ошибётся трижды). HUD слева вместо `{timeLeft}с` показывает
      `🏖 {vacationSlices}/3`, краснеет на 2/3. Экран Game Over различает
      причину окончания (порезаны 3 отпуска vs ручное завершение) только
      текстом первой строки — остальной UI (счёт/рекорд/доска рекордов)
      общий.
- *Забег от дедлайнов* (`components/dino-game.tsx`, Chrome-Dino-стиль):
  DOM-раннер без canvas. Персонаж и препятствия — **настоящие PNG-спрайты**
  (не SVG), нарезанные программно (Python/PIL, белый фон → альфа) из трёх
  исходников, которые прислал пользователь в корень проекта
  (`персонаж.png`, `препятсвия.png`, `фон.png`), и разложенные в
  `public/game/character/*.png` и `public/game/obstacles/*.png`.
  `components/dino-sprites.tsx` теперь просто рендерит `<img>` в
  контейнере с `object-fit: contain` (`Runner`, `DeadlineSprite` и т.д. —
  тонкие обёртки над картинкой, названия компонентов не менялись).
  Персонаж: 1 кадр `idle`, 4 кадра бега (`run1..4`, цикличная смена),
  5 кадров прыжка (`jump1..5`, кадр выбирается по фазе — вверх/пик/вниз
  через скорость `vyRef`), 3 кадра приседа (используется `duck1`).
  Препятствия — 10 иконок из присланного листа (было 7, добавили ещё три
  под неиспользованные иконки): наземные `deadline`, `pile`, `countdown`,
  `report`, `problem` (⚠️), `rework` (мусорка); летящие `mail`, `meeting`,
  `asap`, `chat` (диалоговые пузыри). Иконки-препятствия дообрезаны второй
  раз: на исходном листе под каждой иконкой была декоративная линия-
  разделитель + русская подпись — обе убраны при повторной нарезке
  (детектится разрыв по строкам после силуэта иконки, см. историю чата),
  иначе хитбокс включал невидимую подпись и игрок «умирал в воздухе»
  под текстом. Фон — реальная картинка `public/game/background.png`
  (пустыня/скайлайн/кактусы), тайлится по горизонтали через CSS
  `background-repeat: repeat-x` со сдвигом `bgOffset` для параллакса
  (вместо прежних hand-coded SVG-кактусов/облаков/камешков — компоненты
  `Cloud`/`Rock` убраны из `dino-sprites.tsx`, `Cactus` теперь тоже
  картинка, вырезанная отдельно из того же фона, используется только на
  экране Game Over). Игровое поле — `aspect-[2172/541] max-h-[420px]`
  (пропорции самого фона, раньше было `min-h-[60vh]` и поле было в разы
  больше фоновой картинки). Летящие препятствия при спавне получают
  случайный `flyVariant`: `"duck"` (низко, `FLY_DUCK_MIN/MAX` — надо
  присесть) или `"high"` (высоко, `FLY_HIGH_MIN/MAX` — пробегается понизу
  без каких-либо действий, прыгать под них не нужно; зазор над головой
  минимальный — `FLY_HIGH_MIN=78`, чуть выше роста стоя `STAND_H=72`).
  HUD: `HI`/текущий счёт слева сверху, кнопки паузы/рестарта/выхода
  справа сверху, `Distance` — тоже справа, но ниже кнопок (`top-14`).
  Скорость нарастает со временем, коллизии — AABB (`overlaps`) отдельно
  по X и Y с разными зонами для наземных/летящих препятствий. Рекорд —
  `localStorage["ttt_dino_best"]`. Три исходных PNG остались лежать в
  корне проекта (не в `public/`, поэтому не раздаются) — можно удалить
  вручную, если больше не нужны.

  **Второй раунд правок (после первого деплоя и тестов):** окно игры
  сделали выше (`aspect-[2172/820] max-h-[560px]`, раньше `2172/541
  max-h-[420px]` — оказалось слишком приплюснуто), фон растянут выше
  (`backgroundSize: auto 100%`, было `68%`) и стал прозрачнее
  (`opacity: 0.6`, было `0.85`) для контраста с препятствиями; у
  наземных препятствий добавлена `drop-shadow`, чтобы не казались
  «прозрачными» на фоне пустыни. У 5 иконок (`mail`, `meeting`, `asap`,
  `chat`, `problem`) под силуэтом всё ещё оставалась полоса-разделитель
  (не долез предыдущий алгоритм — полоса иногда даёт даже более высокое
  покрытие по строкам, чем сама иконка, поэтому эвристика «дальше контента
  меньше» её не отсекала) — все 5 вырезаны заново из `препятсвия.png` с
  вручную проверенными по пиксельной сетке границами кропа.
  Главный баг — «после 2–3 партий игра запускается пустая»: `step()` не
  делал `return` после `finishGame()`, из-за чего планировался ещё один
  кадр `requestAnimationFrame`; при быстром рестарте это могло пересечься
  со стартом нового цикла. Добавлена защита через счётчик поколений
  игры — `gameIdRef`: `startGame()` инкрементирует его и передаёт текущее
  значение в `step(myGameId)`, которая в начале и в конце проверяет
  `myGameId === gameIdRef.current` и молча выходит, если это уже не
  актуальная игра (плюс инкремент при размонтировании компонента).
  `startGame()` также заново измеряет размер арены (`arenaRef.current`)
  перед стартом, а `spawnObstacle()` читает ширину напрямую из
  `arenaRef.current?.clientWidth`, а не из state `size`, чтобы не зависеть
  от того, какой рендер «заморозил» замыкание игрового цикла.

  **Третий раунд правок (жалоба: «первый раз хорошо, повторные разы то
  персонаж, то препятствия пропадают, то с персонажем что-то странное»):**
  найден и исправлен реальный баг — оверлеи «игра не идёт»
  (`state !== "playing"`, экран старта/game over) и «пауза» не
  останавливали всплытие клика (`stopPropagation` отсутствовал), в отличие
  от кнопок paus/restart/exit сверху и duck/jump снизу, у которых он есть.
  Из-за этого клик по кнопке внутри оверлея всплывал до `onClick` арены
  (`handleArenaClick` → `jump()`). Конкретно ловится на кнопке
  «Продолжить»: `state` там уже `"playing"`, поэтому клик реально долетал
  до `jump()` и вызывал случайный прыжок сразу при выходе из паузы —
  похоже на «что-то странное с персонажем». Добавлен `onClick={(e) =>
  e.stopPropagation()}` на оба оверлея. Также на всякий случай добавлен
  long-cache заголовок (`Cache-Control: public, max-age=31536000,
  immutable`) на `/game/*` в `next.config.ts` — спрайты не меняются между
  деплоями, а без явного кэша браузер может ревалидировать их при каждом
  заходе, что при плохой сети способно давать заметное мигание/пропажу
  кадров. Полностью ли это устраняет исходную жалобу (спорадическая

  выходе из паузы) — не проверено вживую, стоит перепроверить на реальных
  повторных заездах.

  **Четвёртый раунд правок (жалоба: «скорость то разная, то одинаковая —
  нужна умеренная и постоянная»):** в обеих играх скорость была случайной
  или растущей. В «Забеге от дедлайнов» — разгон `BASE_SPEED → MAX_SPEED`
  через `SPEED_ACCEL` за время забега убран: теперь `BASE_SPEED = MAX_SPEED
  = 8`, `SPEED_ACCEL = 0` — скорость постоянна весь забег. В «Разрезании
  задач» — высота и цель траектории каждой карточки были случайными
  (`heightFactor`, `targetX` в `spawnObject()`), из-за чего скорость полёта
  отличалась от броска к броску; заменены на константы (`heightFactor =
  0.7`, `targetX = w * 0.5` — центр арены, даёт одинаковую по модулю
  скорость что слева, что справа).

  приходят»):** причина — `void notifyUser(...)` в

  довыполняет переданный колбэк до заморозки функции, а клиенту ответ всё

  пользователем напрямую («а сможешь сделать doom?») после того, как ему
  предложили и он отклонил несколько других идей мини-игр (гонка досок и

  вид сверху) на тему «офис-подземелье багов» — противники визуально жуки

    направления + плоскость камеры, техника из тюториалов вроде Lodev —
    общеизвестный алгоритм компьютерной графики, не код и не ассеты
    какой-либо конкретной игры). Внутренний рендер — низкое разрешение
    `320×200` (то самое разрешение старых DOS-шутеров) на `<canvas>`,
    растянутое через CSS `image-rendering: pixelated`; это и быстрее, чем
    рейкастить в реальном разрешении экрана, и даёт узнаваемую
    ретро-картинку. `castRay()` — чистая функция (сетка + позиция +
    направление луча → расстояние/сторона/тип стены), используется и для
    рендера стен, и для проверки «не загорожена ли цель стеной» при
    выстреле.

    каждая колонна появляется случайным образом, поэтому карта немного
    отличается между заездами; кольцо внешних стен гарантирует, что карта
    всегда связная, без риска запертых зон (в отличие от рукописного
    ASCII-лабиринта).

    поворот камеры. Пробел или клик по канвасу — выстрел (первый клик,

      дробовика) не связаны с краем и остаются непрозрачными, в отличие от

      середине спрайтов. После этого — `GaussianBlur` на альфа-канал (лёгкое

      промежуточный результат собирался в контрольный лист (сетка
      миниатюр с подписями) и **прочитан инструментом чтения файлов перед
      тем, как считать вырезку финальной** — тот же приём проверки
      реальным рендером, что и с иконкой катаны ранее в этом же файле;
      два первых варианта кропа ружья (`gun_pose1`) попали на пересечение
      двух разных поз с перекрывающимися стволами и были отброшены после
      визуальной проверки в пользу чистых, не пересекающихся поз из
      второго ряда листа. Итог — 14 PNG в `public/game/shooter/`: 4 врага
      (`enemy-clock/paper/error/coffee.png`), 2 позы дробовика
      (`gun-idle.png`, `gun-fire.png` — используется для короткой анимации
      отдачи при выстреле), вспышка (`muzzle-flash.png`), 2 декали
      (`bullet-hole.png`, `blood-splat.png`), 4 текстуры стен
      (`wall-plain/door/window/whiteboard.png`) и текстура пола
      (`floor-wood.png`).
    - **Подгрузка в компоненте**: `ASSET_PATHS` — только пути (строки),
      сами `new window.Image()` создаются в `useEffect` на маунте, а не в
      module scope — конструктор `Image` есть только в браузере, а модуль
      компонента импортируется и на сервере при SSR (там `Image` не
      определён, был бы краш рендера страницы). Рендер каждый кадр
      проверяет `img.complete && img.naturalWidth > 0` (хелпер `isReady`)
      и рисует картинку, если она готова, либо использует прежний
      сплошной цвет/эмодзи как фоллбэк — так первые один-два кадра до
      подгрузки (обычно доли секунды, старт игры и так за экраном выбора)
      не ломаются, просто чуть более простые визуально.
    - **Текстурированные стены**: раньше — одна заливка на весь столбец;
      теперь для каждого столбца экрана считается `wallX` — дробная
      координата точки попадания луча вдоль грани стены (`posY +
      dist*rayDirY`, минус целая часть, либо через X-компоненту для
      другой стороны грани — стандартная формула из того же класса
      техник, что и сам DDA), из неё — `texX`, столбец текстуры шириной в
      1px, растянутый на всю высоту сегмента через `ctx.drawImage` с
      исходным прямоугольником `(texX, 0, 1, texH)`. Зеркалирование по
      направлению луча (иначе текстура на стенах, обращённых в разные
      стороны, читалась бы отражённой) — стандартная поправка `texX =
      texW - texX - 1` в зависимости от знака `rayDirX`/`rayDirY` и
      стороны грани. Поверх текстуры — то же самое затемнение по стороне
      грани и дальности, что было раньше (полупрозрачный чёрный
      прямоугольник), чтобы не терять ощущение глубины теперь, когда
      цвет задаёт не заливка, а картинка. 4 типа стен (`WALL_TEX_KEY`)
      сохранили прежнюю смысловую раскладку: обычная перегородка →
      `wall-plain`, «серверная» пилон → `wall-door`, «переговорка» →
      `wall-window` (стекло/жалюзи по смыслу подошло идеально), декор-
      колонна → `wall-whiteboard`.
    - **Пол**: честный per-pixel floor-casting (отдельный луч на каждый
      пиксель пола с перспективным делением) — заметно дороже по кадру и
      сильно усложнил бы код ради разницы, которую на 320×200
      внутреннем разрешении почти не видно; вместо этого — дешёвый
      компромисс: `ctx.createPattern(floorImg, "repeat")` замащивает
      нижнюю половину экрана текстурой паркета как есть (без перспективной
      коррекции), поверх — вертикальный градиент затемнения от горизонта
      (тёмный, «в тумане») к низу экрана (светлее, «рядом»), тот же приём,
      что и туман на стенах. Потолок остался плоским градиентом (был
      сплошной заливкой) — здесь настоящий кит подвесного офисного потолка
      среди вырезанных ассетов не подходил по ракурсу (все ассеты сняты
      сверху для топ-дауна, а не как потолок снизу).
    - **Враги-биллборды**: `Enemy` получил поле `kind` (0–3, случайное при
      спавне в `spawnWave` — `Math.floor(Math.random()*4)`), волны теперь
      визуально разнородные вместо одинаковых жуков-эмодзи. Каждый тип
      рисуется через `drawImage` с сохранением исходных пропорций спрайта
      (`spriteWidth = spriteHeight * naturalWidth/naturalHeight` — портреты
      четырёх монстров разной ширины/высоты, растягивать до квадрата было
      бы заметно). Поверх — то же дальностное затемнение, что и у стен,
      для единого ощущения глубины между стенами и спрайтами. Пикапы (☕)
      остались эмодзи — под них не было отдельного ассета на листах (только
      монстр «Кофейный монстр» целиком, с лицом и руками — использовать
      его как маленькую иконку аптечки выглядело бы странно).
    - **Дробовик и отдача**: `drawGun()` переписан на реальные спрайты
      руки с дробовиком вместо трёх залитых прямоугольников. Два кадра —
      `gun-idle` (обычное удержание) и `gun-fire` (более выраженный
      прогиб/перезарядка), переключение по `muzzleTimerRef` (пока идёт
      таймер вспышки — на экране кадр «выстрел»). Вспышка (`muzzle-flash.png`)
      рисуется рядом со стволом с угасающей прозрачностью
      (`globalAlpha = timer/MUZZLE_FLASH_MS`), а не быстрым морганием
      видимо/невидимо — плавнее.
    - **Декали как обратная связь на попадание**: раньше выстрел никак не
      показывал, попал он или нет, кроме исчезновения противника. Теперь
      `hitFlashRef`/`missFlashRef` (мс) запускаются в `fire()` — при
      попадании по врагу коротко показывается `blood-splat.png` у прицела,
      при попадании в стену/промахе — `bullet-hole.png`, оба гаснут через
      `HIT_FLASH_MS` (220мс) по той же схеме плавного угасания через
      `globalAlpha`. Дополнительно — красная виньетка на весь экран
      (`ctx.createRadialGradient`) при получении урона от монстра
      (`damageFlashRef`, 260мс) — дешёвый, но заметный сигнал «вас
      ударили», особенно важный в шутере, где раньше единственной
      обратной связью было падение числа в HUD.
    - **Переименование**: заголовок карточки и описание в
      `game-picker.tsx` — «Отстрел задач» / «Рейкастер-шутер:
      расстреливайте офисных монстров дробовиком волна за волной»,
      иконка карточки `Bug` → `Target` (раз враги теперь не абстрактные
      баги, а узнаваемые офисные монстры). Внутренний `GameId`/`gameId`
      остался строкой `"doom"` — это только программный идентификатор
      (ключ в БД, файл компонента `doom-game.tsx`), пользователю нигде не
      показывается, поэтому его смена ничего не сломала бы, но и не давала
      никакой пользы — оставлен как есть, чтобы не трогать схему БД/API
      без необходимости. Счётчик побед в HUD — иконка `Skull` вместо `Bug`
      (тоже по той же причине: жуков в игре больше нет, есть монстры).
      Тексты финального экрана и подсказки обновлены под новую тематику
      («вас доконали офисные монстры», «в атаку», список названий монстров
      вместо общего слова «баги»).
  - **Третий раунд — замена стен/пола/оружия на ассеты, сгенерированные по
    промтам, и починка тёмного квадрата вокруг врагов** (пользователь
    сгенерировал `мгмга.png` (стены), `ксео.png` (пол), `ывсыв.png` (руки с
    ружьём) по промтам, которые я дал ему специально под требования
    рейкастера — фронтальный вид без перспективы, ровный свет, бесшовность
    — и попросил заменить старые ассеты на них, плюс убрать тёмный
    полупрозрачный квадрат вокруг противников):
    - `мгмга.png` — 2×2 сетка из 4 стен (обычная, с дверью, с окном/
      жалюзи, с доской) на белом фоне с тонким белым зазором между
      ячейками; никакого хромакея не потребовалось (это не спрайты с
      прозрачностью, а цельные непрозрачные фотографии стен) — просто
      нарезаны по сетке (границы найдены поиском белых строк/столбцов
      через numpy, не на глаз) и уложены поверх старых `wall-*.png` в
      `public/game/shooter/`, имена файлов не менялись, поэтому правки
      кода не потребовались.
    - `ксео.png` — уже готовая бесшовная плитка паркета «ёлочкой» на весь
      кадр, без рамки и подписей — использована как есть, без обрезки,
      заменила `floor-wood.png`.
    - `ывсыв.png` — рука с помповым дробовиком на светлом (почти белом)
      шахматном фоне-подложке (та же ситуация, что и с предыдущим листом
      оружия: сам PNG на диске без реального альфа-канала, `mode="RGB"`,
      несмотря на то, что визуально выглядит как прозрачность). Ключевое
      отличие от первого прохода извлечения ассетов — здесь фон **светлый**
      (яркость ~243–255), а не тёмный, поэтому маска фона строилась по
      условию «ярче порога», а не «темнее» (`keyout_light_bg` в
      `crop_assets2.py`), с тем же приёмом «в прозрачные превращаются
      только связные области, касающиеся края кропа», чтобы светлые тона
      кожи руки не выело. Только одна поза (в отличие от штатного листа с
      несколькими кадрами) — используется и как `gun-idle.png`, и как
      `gun-fire.png` (тот же файл под обоими именами); ощущение выстрела
      по-прежнему даёт кадр отдачи (сдвиг вниз на `recoilRef`) и вспышка
      дульного среза, а не смена позы руки — с одной позой это не выглядит
      хуже, просто чуть проще.
    - Все новые изображения были в разы больше, чем нужно для внутреннего
      разрешения рендера 320×200 (стены/пол — под 1250px, дробовик —
      1536px по стороне), поэтому перед тем как класть их в `public/`,
      каждое уменьшено (`PIL.Image.resize`, `LANCZOS`) до реалистичного
      максимума — стены и пол до 480–512px по длинной стороне, дробовик до
      560px — иначе игра тянула бы с сервера по 2–3 МБ на каждую текстуру
      без всякой пользы для итоговой картинки.
    - **Починка тёмного квадрата вокруг врагов**: затемнение по дальности
      для спрайтов противников рисовалось как `ctx.fillRect` поверх всего
      bounding box спрайта (`spriteWidth × spriteHeight`) полупрозрачным
      чёрным — но у PNG врага прозрачные углы (силуэт не квадратный), а
      `fillRect` заливает прямоугольник целиком независимо от прозрачности
      уже нарисованного под ним, поэтому вокруг каждого монстра был виден
      лишний тёмный полупрозрачный квадрат, особенно заметный на светлом
      полу. Первая попытка исправить через `globalCompositeOperation =
      "source-atop"` не помогла бы (композитинг сравнивается с уже
      нарисованным на *всём* канвасе — там к этому моменту уже сплошной
      пол/стены, а не только силуэт врага, так что "source-atop" всё равно
      залил бы весь прямоугольник). Правильное исправление — canvas-фильтр
      `ctx.filter = "brightness(...)"`, выставленный перед тем самым
      `drawImage()` спрайта врага и сброшенный сразу после: фильтр
      применяется только к пикселям, которые непосредственно рисует этот
      вызов, поэтому прозрачные уголки спрайта остаются прозрачными, а
      затемнение получает только сам силуэт монстра.
  - **Esc — пауза с выходом, а не просто снятие мыши**: браузер и так снимает
    Pointer Lock по Esc (это его собственное поведение, JS его не
    отменяет), но раньше игра при этом не останавливалась — она продолжала
    идти за невидимым курсором, а чтобы дотянуться до кнопок паузы/выхода,
    приходилось кликать по канвасу, что тут же захватывало указатель
    обратно. Теперь `Escape` в обработчике `onKeyDown` явно вызывает
    `togglePause()` (то же самое, что кнопка паузы) — курсор освобождается,
    и сразу открывается оверлей паузы. В этот оверлей добавлена вторая
    кнопка «Выйти» (`onExit`) рядом с «Продолжить», раньше там была только
    одна кнопка — так что после Esc не обязательно сначала возобновлять
    игру, чтобы добраться до выхода из мини-игры на экран выбора.
  - **Четвёртый раунд — жалоба «стены что-то непонятное, всё друг на
    друге» + «пол» + «руки с ружьём не заменили»**: пользователь
    сгенерировал новые ассеты по промтам (см. выше) и заменил старые файлы
    под теми же именами (`wall-*.png`, `floor-wood.png`, `gun-idle/fire.png`
    в `public/game/shooter/`), но в браузере всё выглядело так, будто
    ничего не поменялось — стены как в самой первой версии (с «рамкой» от
    офисного кита), пол в мелкую шашечку, оружие похоже на старое. Нашлись
    сразу три разные причины, все под одной жалобой:
    - **Иммутабельный кэш**: `/game/:path*` отдаётся с `Cache-Control:
      public, max-age=31536000, immutable` (см. `next.config.ts`) —
      специально, чтобы спрайты не мигали на плохой сети. Но при замене
      содержимого файла **под тем же именем** браузер (и CDN) вправе
      никогда не перезапрашивать его заново — именно поэтому после замены
      картинок на диске в браузере всё ещё было видно старьё. Исправлено
      версионным query-параметром: `ASSET_VERSION = "v3"` подставляется в
      конец каждого пути в `ASSET_PATHS` (`wall-plain.png?v3` и т.д.) —
      меняется сам URL, кэш обходится гарантированно. При следующей смене
      любого спрайта в `public/game/shooter/` нужно не забыть увеличить
      `ASSET_VERSION`, иначе эта же проблема повторится.
    - **«Всё друг на друге» на стенах — не баг, а несоответствие масштаба
      текстуры и клетки карты**: `wall-plain.png` — это фотография целой
      стены с 3 видимыми панелями и плинтусом, но она натягивалась на
      **одну** клетку карты шириной в 1 юнит (`wallX` в `[0,1)`). Карта —
      открытый зал, и когда смотришь вдоль длинной границы (а не строго
      перпендикулярно ей), в кадре одновременно видно много клеток подряд —
      каждая рисует ту же самую фотографию целиком, сжатую в свою узкую
      полоску, из-за чего длинная стена превращается в частокол
      одинаковых мелких «рамок». Исправлено константой `WALL_TEX_SPAN`
      (`{1: 3, 2/3/4: 1}`) — обычная стена растягивается на 3 клетки вместо
      1 (её 3 панели естественно ложатся по одной на клетку), а не
      повторяется трижды внутри одной. Заодно исправлена и вторая причина
      того же визуального «нагромождения»: колонны с дверью/окном/доской
      были 2×2 клетки, а сама картинка на них — цельная сцена «одна дверь
      на всю грань»; с гранью в 2 клетки и `wallX` в `[0,1)` на каждой из
      двух клеток эта же дверь рисовалась заново, то есть на одной стене
      было видно две одинаковые двери подряд. `buildMap()` теперь ставит
      такие колонны 1×1 — ровно по размеру текстуры, без повтора и без
      обрезки.
    - **«Пол в шашечку» — алиасинг мелкого узора, а не баг рендера**:
      `ксео.png` — качественная бесшовная плитка паркета 512×512 с высокой
      частотой мелких деталей (тонкие волокна дерева). Внутреннее
      разрешение канваса — всего 320×200, а нижняя половина (пол) занимает
      320×100 — то есть один тайл 512×512 в эту область не помещается
      целиком и не повторяется вообще (не видно тайлинга), а мелкий узор
      попадает под агрессивное уменьшение и алиасится в шумную
      «шашечку» (плюс — картинка в любом случае растягивается на реальный
      размер экрана через CSS `image-rendering: pixelated`, что ещё усиливает
      блочность при масштабировании уже испорченного кадра). Исправлено
      уменьшением `floor-wood.png` до 110×110 перед тем, как класть его в
      `public/` — при таком размере тайл реально повторяется несколько раз
      по ширине пола (`createPattern(..., "repeat")` заметно тайлится, а не
      просто показывает обрезок одной текстуры), и мелких деталей,
      которые могли бы заалиасить, в принципе меньше.
  - **Пятый раунд — не видно очков** (жалоба: «не показывается сколько
    очков заработано в стрелялке»): формула очков (`kills*10 +
    (wave-1)*25`) считалась только один раз, внутри `finishGame()`, ради
    отправки на доску рекордов — нигде в интерфейсе само число не
    показывалось, только отдельно «убито» и «волна». Вынесена в общую
    `computeScore(kills, wave)`, чтобы формула не разъезжалась между тремя
    местами использования: HUD во время игры (новая строка «Очки: N» под
    счётчиком убитых/волны, с разделительной чертой), финальный экран
    (крупным текстом над «N побеждено · волна N», как раньше), и сама
    отправка в `finishGame()`.

**Telegram-бот** (`https://t.me/diytask_tracker_bot`): привязка
аккаунта — кнопка «Telegram-бот» в шапке (`telegram-link-dialog.tsx`)
запрашивает `POST /api/telegram/link`, получает одноразовый токен

пользователь открывает его в Telegram, бот в `/start` подтверждает
привязку (`setTelegramLink`, таблица `telegram_links`, один чат на
email). Дальше бот понимает команды `/mytasks` (все не-done задачи
пользователя во всех досках всех его пространств), `/today` (только
просроченные/на сегодня), `/questions` (открытые вопросы), `/help`.
Уведомления — `notifyUser()` из `lib/telegram.ts`, дергается при
назначении задачи на пользователя (создание и переназначение через
`PATCH /api/tasks/[id]`) и при новом вопросе/ответе в вопросе; в
сообщении о задаче — инлайн-кнопки «Открыть» (диплинк в приложение) и
«✅ Готово» (`callback_data: done:<taskId>`, обрабатывается вебхуком,
проверяет что нажавший — назначенный исполнитель, ставит этап `done`
и правит текст сообщения); те же кнопки «✅ Готово» — по одной на
задачу — добавлены и в списки `/mytasks`/`/today`
(`editMessageReplyMarkup` в `lib/telegram.ts` убирает только нажатую
кнопку из клавиатуры, не трогая текст списка; `handleCallbackQuery`
различает список от одиночного уведомления по числу строк клавиатуры).
Ответы на вопросы синхронизируются в обе
стороны: уведомление о вопросе содержит скрытый маркер
`<code>Q:{id}</code>», и если пользователь отвечает (reply) прямо на
это сообщение в Telegram, вебхук вытаскивает id вопроса из
`reply_to_message.text` и создаёт `QuestionMessage` от его имени.
Ежедневный дайджест (просрочки/сегодня/открытые вопросы) — cron
`vercel.json` → `/api/cron/telegram-digest`, раз в сутки (04:00 UTC),
защищён `CRON_SECRET` (bearer-токен, сверяется с заголовком
`Authorization`, если секрет задан). `notifyUser()` и вебхук никогда
не бросают исключений наружу — сбой Telegram API (нет линка, нет
токена, таймаут) не должен ронять основной запрос создания задачи/
вопроса.

**Google Calendar — виджет «Сегодня»** (`components/calendar-widget.tsx`,
справа от досок на `/w/[workspaceId]/boards`, `lib/google-calendar.ts`):
показывает встречи текущего пользователя на сегодня из его личного
Google-календаря (`primary`, только чтение — scope
`calendar.readonly`). Привязка не завязана на пространство — один
Google-аккаунт на email, общий для всех пространств пользователя.

Если `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` не заданы
(`isGoogleCalendarConfigured()`), виджет просто показывает заглушку
«ещё не настроен на сервере» вместо кнопки подключения — можно
деплоить без Google-интеграции, ничего не ломается.

OAuth-флоу: кнопка «Подключить» → `GET /api/google-calendar/connect`
(генерирует случайный `state`, кладёт в куку `gcal_oauth_state`,
редиректит на экран согласия Google с `access_type=offline` и
`prompt=consent` — иначе Google не пришлёт `refresh_token` повторно
при переподключении) → пользователь соглашается → Google редиректит на
`GET /api/google-calendar/callback` (сверяет `state` с кукой — защита
от CSRF, меняет `code` на пару токенов, сохраняет в БД) → назад на
доску с `?calendar=connected` (тост) либо `?calendar_error=...` (тост
с текстом ошибки: `not_configured`/`state`/`denied`/`failed`). Токены —
`google_calendar_links` (`email` PK, `access_token`, `refresh_token`,
`expiry_date`), `access_token` обновляется через `refresh_token`
автоматически при каждом запросе, если истёк (запас 60с). Если
`refresh_token` отозван пользователем в его Google-аккаунте (или
Google вернул 401 при запросе событий) — привязка удаляется и виджет
просит переподключиться (`needsReconnect: true`), а не падает молча.
Кнопка «Обновить» дёргает `GET /api/google-calendar/events` без
перезагрузки страницы, «отключить» (иконка `Unlink`) — `POST
/api/google-calendar/disconnect`, просто удаляет привязку из БД (сам
доступ в Google-аккаунте пользователя при этом не отзывается — это
можно сделать только на стороне Google, в разделе «Стороннее приложения
и сервисы»).

**Расширение Telegram-бота, внутриприложенческие уведомления, история
задачи, поиск/фильтры, рассылка админа, самосброс пароля** (один большой
заход, все — аддитивно поверх существующего, ничего из описанного выше не
удалялось и не меняло поведения по умолчанию):

- **Единый диспетчер уведомлений** (`lib/notifications.ts`, функция
  `notify(event)`): каждое уведомление теперь всегда пишется в
  внутриприложенческий «колокольчик» (таблица `notifications`) и, если у
  адресата привязан и настроен Telegram, дублируется туда же. Все прежние
  прямые вызовы `notifyUser()` в `app/api/tasks/route.ts`,
  `app/api/tasks/[id]/route.ts`, `app/api/questions/route.ts`,
  `app/api/questions/[id]/messages/route.ts` и в вебхуке (ответ на вопрос
  через reply) заменены на `notify()`. `notifyUser()`/`sendMessage()` в
  `lib/telegram.ts` остались как есть — `notify()` вызывает их внутри.
- **Настройки уведомлений на пользователя** (`telegram_links` — новые
  колонки `username`, `notify_task_assigned`, `notify_comments`,
  `notify_stage_changes`, `notify_task_deleted`, `notify_questions`,
  `notify_digest`, `digest_hour_utc`): переключатели в диалоге
  «Telegram-бот» (`telegram-link-dialog.tsx`, дергает
  `GET/PATCH /api/telegram/prefs`) — каждое событие можно приглушить
  отдельно, в колокольчике оно всё равно останется. `notify()` перед
  отправкой в Telegram проверяет соответствующий `prefKey`; события без
  своего переключателя (админ-рассылка) уходят всем, у кого бот вообще
  привязан.
- **История задачи** (комментарии + автолог изменений, таблица
  `task_events`, роут `app/api/tasks/[id]/events/route.ts`,
  UI — секция «История» в `task-dialog.tsx`, ниже «Комментария
  исполнителя»): любой участник пространства может оставить комментарий
  (не только создатель/исполнитель — это отдельная лента, не
  `resultNote`, который как был единственным «итоговым» полем
  исполнителя, так и остался). Смена этапа/приоритета/исполнителя/срока
  через `PATCH /api/tasks/[id]` теперь автоматически пишет системную
  запись в ту же ленту (`createTaskEvent`, сравнение `existing` vs новое
  значение). Комментарий уведомляет «другую сторону» задачи
  (`notifyComments`), смена этапа — постановщика, если менял не он
  (`notifyStageChanges`), удаление задачи — исполнителя и постановщика
  (`notifyTaskDeleted`).
- **Внутриприложенческие уведомления / колокольчик**
  (`components/notification-bell.tsx` в шапке рядом с аватаром,
  роуты `app/api/notifications/route.ts` GET список+POST «прочитать
  всё», `app/api/notifications/[id]/route.ts` PATCH одно): работает
  независимо от Telegram — красный бейдж с числом непрочитанных, клик по
  уведомлению ведёт по `link` и отмечает прочитанным. Поллинг ~35 сек по
  тому же паттерну, что и остальной polling в приложении (пауза при
  скрытой вкладке).
- **Поиск и фильтры задач** (`kanban-board.tsx`, `my-tasks-board.tsx`):
  строка поиска (title+description), фильтры по приоритету/исполнителю/
  сроку (просрочено/сегодня) — чисто клиентские, без новых API, поверх
  уже загруженного списка задач. Тумблер «Только мои задачи» (был на
  доске, с ключом `ttt_filter_mine` в localStorage) позже убран отдельным
  запросом — см. ниже, в самом верху документа, где он уже помечен
  удалённым.
- **Фильтр по статусам** (`components/status-filter-dropdown.tsx`,
  используется в `kanban-board.tsx` и `my-tasks-board.tsx`,
  `StatusFilterValue = "all" | "open" | "closed"`): выпадающий список
  ровно по образцу присланного пользователем скриншота — «Любой статус» /
  «Открытые задачи» / «Закрытые задачи», без отдельного варианта на
  каждый этап канбана. «Открытые» — всё, что не в этапе «Готово»
  (`todo`+`in_progress`+`review`), «Закрытые» — только `done`. Колонки
  канбана (все 4) при любом фильтре остаются на месте — фильтруются
  только сами задачи внутри них (`visibleTasks`); колонка «Готово» не
  пропадает при фильтре «Открытые задачи», просто пустеет (плейсхолдер
  «Нет подходящих задач»). Самописный
  компонент (не `DropdownMenu` из `components/ui/`) — нужен контроль над
  поворотом шеврона и подсветкой кнопки при открытой панели. Более ранние
  версии этого фильтра (сначала мульти-чипы на каждый этап, потом
  одиночный выбор конкретного этапа) заменены этой — не сохранились.
  История изменения статуса — отдельная, уже описанная выше фича
  («История задачи», `task_events`, тип `stage_changed`): каждая смена
  этапа логируется автоматически и видна в разделе «История» диалога
  задачи вместе с комментариями, путать с фильтром колонок не стоит.
  Сама секция «История» в `task-dialog.tsx` — теперь сворачиваемая
  (`historyOpen`, по умолчанию `false`): заголовок с бейджем-счётчиком
  и шевроном кликабелен, разворачивает/сворачивает список + поле ввода
  комментария; события всё равно подгружаются сразу при открытии
  диалога (не дожидаясь разворота), чтобы счётчик в заголовке был
  верным без лишнего клика. Сбрасывается в свёрнутое состояние при
  каждом открытии диалога/смене задачи.
- **Убраны фильтры приоритета и срока** из тулбаров `kanban-board.tsx` и
  `my-tasks-board.tsx` (были `<Select>` «Все приоритеты» и «Все сроки» +
  состояния `priorityFilter`/`dueFilter`, `type DueFilter`). Остались:
  поиск, `StatusFilterDropdown` (см. выше) и фильтр по исполнителю.
  `PRIORITIES`/`PriorityId`/`isDueToday`/`isOverdue` больше не
  импортируются в этих файлах.
- **Недельное архивирование «Готово»** (`lib/week.ts`,
  `Task.completedAt`) — для длительных командных досок, где список
  готовых задач иначе растёт бесконечно. Правило: по умолчанию в колонке
  «Готово» видны только задачи, завершённые в текущую неделю; как только
  неделя закончилась, они пропадают из вида по умолчанию (но не
  удаляются — видны через выбор недели). Реализация целиком на бэке, как
  просил пользователь, — фронт не считает даты сам:
  - `Task.completedAt: string | null` — когда задача в последний раз
    перешла в этап «Готово». Выставляется только на сервере, в
    `PATCH /api/tasks/[id]`: при входе в `done` — `new Date().toISOString()`,
    при выходе из `done` — `null`. Колонка `completed_at TIMESTAMPTZ` в
    Postgres (`lib/schema.sql.ts`), с бэкфиллом `completed_at = updated_at`
    для уже готовых задач старой схемы (**нужно `npm run db:migrate`**).
  - `lib/week.ts` — ISO 8601 недели (понедельник — начало, номер недели
    от первого четверга года, посчитано в UTC): `getWeekKey`,
    `getCurrentWeekKey`, `getWeekRange`, `isInWeek`, `formatWeekLabel`
    (человекочитаемая подпись на русском, например «7–13 июля 2026»),
    `formatWeekLabelShort` (добавляет «Эта неделя (…)» для текущей),
    `filterDoneTasksByWeek` (не-«готово»-задачи не трогает, «готово» —
    только если `completedAt` в этой неделе, с фолбэком на `updatedAt`
    для старых записей без `completedAt`), `collectDoneWeeks` (список
    недель с количеством, новые сверху — для UI-пикера).
  - `GET /api/boards/[id]` и `GET /api/tasks/mine` принимают
    `?doneWeek=<weekKey>` (по умолчанию — текущая неделя), отдают
    `tasks` уже отфильтрованными плюс `doneWeek`/`doneWeeks` в ответе.
    SSR-страницы (`boards/[id]/page.tsx`, `my-tasks/page.tsx`) применяют
    ту же фильтрацию на первом рендере — иначе клиент «моргнул» бы
    лишними задачами до первого polling. На `my-tasks` есть исключение:
    если открываем по ссылке из уведомления задачу, которая не попала в
    текущую неделю (`?taskId=...`), она всё равно подмешивается в
    список — иначе диалог открылся бы на пустом месте.
  - **UI**: `components/week-picker.tsx` — маленькая кнопка-календарь с
    выпадающим списком недель (по образцу `status-filter-dropdown.tsx`).
    Показывается **только** в колонке «Готово» и только когда
    `StatusFilterDropdown` = «Любой статус» (`stageFilter === "all"`) —
    осознанно спрятан при «Открытые»/«Закрытые», чтобы не плодить лишний
    UI. Выбор недели триггерит немедленный fetch (не ждёт фоновый
    polling каждые 12 сек), сам polling тоже передаёт текущую выбранную
    неделю через `doneWeekRef`, чтобы не откатывать выбор пользователя.
  - Важно: фильтрация по неделе на бэке применяется **всегда** (нет
    отдельного «безлимитного» режима на сервере) — есть только та неделя,
    что просит клиент через `?doneWeek=`, либо специальное значение
    `ALL_WEEKS = "all"` (`lib/week.ts`), которое означает «не фильтровать,
    отдать все недели» (`filterDoneTasksByWeek` в этом случае просто
    возвращает список как есть).
  - **Уточнение поведения для «Закрытые задачи»** (жалоба: «при выборе
    закрытые пропадает фильтр по неделям, а должны сначала показываться
    все закрытые, но с пометкой недели, и чтобы можно было сузить»):
    пикер недели теперь показывается не только при «Любой статус», но и
    при «Закрытые задачи» (`stageFilter === "all" || stageFilter ===
    "closed"` в обоих компонентах). Дефолт `doneWeek` зависит от того, в
    какой фильтр переключились — отслеживается через `prevStageFilterRef`
    (реагирует именно на *смену* `stageFilter`, не на каждый рендер):
    переход в «Закрытые» ставит `doneWeek = ALL_WEEKS` (сразу весь архив),
    возврат из «Закрытые» в «Любой статус» — обратно `getCurrentWeekKey()`
    (чтобы в обычном виде колонка «Готово» не разрасталась). Сам `WeekPicker`
    получил пункт «Все недели» первым в списке (с суммарным счётчиком) —
    добавляется в самом компоненте, не в `collectDoneWeeks`. Когда
    `doneWeek === ALL_WEEKS`, на карточках готовых задач показывается
    бейдж недели (`showCompletedWeek` в `TaskCard`, зелёный, с иконкой
    `CalendarCheck` — не путать с `CalendarClock` у дедлайна): «Готово: 7–13
    июля 2026», через новый `getTaskCompletedWeekKey()` в `lib/week.ts`.
    Бейдж скрыт, когда выбрана одна конкретная неделя — там и так все
    карточки одной недели, подпись избыточна.
- **Бот — переработка UX** (`lib/telegram.ts`, `app/api/telegram/webhook/route.ts`):
  - Ретраи с экспоненциальным бэкоффом на вызовах Bot API (429 — уважаем
    `retry_after` от Telegram, 5xx/сетевые сбои — до 3 попыток) — раньше
    один неудачный `fetch` терял уведомление молча.
  - Постоянное меню внизу чата (`ReplyKeyboard`, кнопки «📋 Мои задачи» /
    «🔥 Сегодня» / «❓ Вопросы» / «❔ Помощь») — присылается после `/start`
    и на `/help`, дублирует команды для тех, кто не любит печатать слэши.
    Список команд-подсказок (`/setMyCommands`) регистрируется через
    `npm run telegram:webhook` (скрипт расширен, вызывает `setMyCommands`
    после `setWebhook`).
  - `/mytasks` и `/today` — пагинация по 8 задач (`buildTasksPage`,
    callback `mt:{offset}`/`td:{offset}`, кнопки «← Назад»/«Ещё →» через
    `editMessageText`), раньше был жёсткий обрез на 15 без возможности
    посмотреть остальное.
  - `/unlink` — отвязать бота прямо командой, без захода в приложение.
    Команды регистронезависимы.
  - На уведомлении о назначении задачи — кнопки «▶️ В работу»
    (`callback_data: start:<id>`, ставит этап `in_progress`) и
    «📅 +1 день» (`callback_data: snooze:<id>`, сдвигает `dueDate` на
    сутки от текущего срока или от «сегодня», если срока не было) —
    рядом с уже существовавшей «✅ Готово».
  - Ник (`username`) из Telegram сохраняется при `/start` и показывается
    в диалоге привязки («Привязано как @ник»).
- **Персонализированный дайджест**: `app/api/cron/telegram-digest/route.ts`
  на каждый прогон шлёт сообщение только тем, у кого текущий UTC-час
  совпадает с их `digest_hour_utc` (по умолчанию 4, меняется в том же
  диалоге привязки) и включён `notify_digest`. **Расписание в
  `vercel.json` осталось `"0 4 * * *"` (раз в сутки) — Vercel Hobby-план
  не разрешает cron чаще раза в день** (пробовали `"0 * * * *"`, деплой
  упал с ошибкой апгрейда до Pro). Из-за этого персональный час реально
  работает только для тех, кто оставил дефолтные 4 UTC — сама
  фильтрация по часу в коде рассчитана на почасовой вызов и заработает
  «из коробки», если: (а) перейти на Vercel Pro и вернуть
  `"0 * * * *"`, либо (б) дёргать `GET /api/cron/telegram-digest`
  раз в час извне (cron-job.org, GitHub Actions и т.п.) с
  `Authorization: Bearer <CRON_SECRET>`.
- **Рассылка администратора** (`components/admin-broadcast.tsx` на
  `/admin`, роут `app/api/admin/broadcast/route.ts`): выбор пространства
  + текст → уходит всем участникам пространства через `notify()` (тип
  `broadcast`, без привязки к конкретному `prefKey` — см. выше).
- **Самостоятельный сброс пароля через Telegram** (без email-инфраструктуры,
  раз она и так не заведена в проекте): `/forgot-password` →
  `POST /api/auth/forgot-password {email}` — если у аккаунта привязан
  бот, туда уходит одноразовая ссылка (`password_reset_tokens`, TTL 30
  мин, `createPasswordResetToken`/`consumePasswordResetToken`) на
  `/reset-password?token=...`, где новый пароль ставится через
  `POST /api/auth/reset-password` (переиспользует существующий
  `resetUserPassword` из store-слоя). Ответ `forgot-password` всегда
  `{ok:true}` независимо от того, существует ли email и привязан ли
  бот — чтобы не палить список зарегистрированных адресов. Если бот не
  привязан, самосброс недоступен — остаётся прежний путь (админ сбрасывает
  пароль вручную в `/admin`).

## Архитектура

- `lib/data.ts` — фасад: выбирает `store-memory.ts` (in-memory) или
  `store-db.ts` (Postgres) по наличию `DATABASE_URL` (`lib/db.ts`).
  Все API-роуты и страницы импортируют функции только отсюда.
- `lib/schema.sql.ts` — идемпотентный DDL (`CREATE TABLE IF NOT EXISTS` +
  `ALTER TABLE ADD COLUMN IF NOT EXISTS`), включает `DO $$...$$` блоки
  бэкфилла легаси-данных в дефолтное пространство. Прогонять через
  `npm run db:migrate` (`scripts/migrate.ts`) после каждого изменения схемы.
- `lib/session.ts` — HMAC-подпись кук, `getCurrentUser()`/`requireAdmin()`.
- `lib/access.ts` — `canAccessWorkspace(user, workspaceId)` (admin — bypass).
- `lib/task-sort.ts` — общий компаратор сортировки задач + `isOverdue`/`isDueToday`.
- UI-примитивы в `components/ui/` — самописные (Dialog, DropdownMenu,
  Select и т.д.), без Radix/`@base-ui/react` — были риски с версией пакета.
- Дизайн-токены — CSS-переменные в `app/globals.css` (`--color-signal`,
  `--color-urgent` и т.д.), стиль «диспетчерская», без generic cream+terracotta.
- `scripts/set-admin.ts` — bootstrap-скрипт для ручного создания
  админ-аккаунта в обход застрявшего seed-потока.
- `lib/telegram.ts` — тонкая обёртка над Telegram Bot API через голый
  `fetch()` (без доп. зависимостей): `sendMessage`/`editMessageText`/
  `answerCallbackQuery`/`setWebhook`, `notifyUser(email, text, opts)`
  (резолвит email → chatId через `telegram_links`, no-op если не
  привязан), инлайн-клавиатуры (`InlineKeyboard`), `boardDeepLink`/
  `questionsDeepLink`. `lib/telegram-digest.ts` — сборка текста
  ежедневной сводки (`buildDailyDigest(email)`), переиспользует
  `isOverdue`/`isDueToday` из `lib/task-sort.ts`. Роуты:
  `app/api/telegram/link/route.ts` (GET статус/POST выдать токен и
  диплинк/DELETE отвязать), `app/api/telegram/webhook/route.ts`
  (входящие апдейты от Telegram), `app/api/cron/telegram-digest/route.ts`
  (вызывается Vercel Cron по расписанию в `vercel.json`).
- `scripts/set-telegram-webhook.ts` — одноразовый скрипт регистрации
  вебхука (`npm run telegram:webhook`), по образцу `scripts/migrate.ts`
  (та же загрузка `.env`/`.env.local` через dotenv).

## Важные решения

- **PATCH /api/tasks/[id]** намеренно не перепроверяет доступ к
  пространству на каждый вызов (ради скорости drag-and-drop) — полагается
  на непредсказуемость ID задачи + обязательную авторизацию. Известный
  компромисс, не абсолютная защита.
- `resultNote` (комментарий исполнителя) редактирует только
  `assigneeEmail === currentUser` — enforced и в UI, и на сервере.
- `createdBy` nullable: если создатель удалён/не известен — редактирование
  открыто всем с доступом к доске (не блокируется намертво).
- Supabase: обязательно Transaction Pooler (порт 6543), не Session
  Pooler (5432) — иначе `EMAXCONNSESSION` под serverless-нагрузкой.
  `vercel.json` пинит регион `sin1` под регион Supabase.
- `lib/pg-client.ts`: `Pool` с `max: 3`, короткий `idleTimeoutMillis` —
  под serverless-профиль нагрузки.
- Скриншоты к задачам хранятся как base64 в Postgres (`task_attachments.data`),
  а не в Vercel Blob/Supabase Storage/S3 — сознательно, чтобы не заводить
  новую инфраструктуру и токены. Лимит 5 файлов × 5 МБ на задачу — при
  реальном использовании стоит следить за размером БД и, если станет
  тесно в `Pool` (`max: 3`), рассмотреть перенос в настоящее файловое
  хранилище.
- `notifyUser()` спроектирован «тихим»: любая ошибка (нет привязки,
  Telegram недоступен, невалидный токен) молча логируется и глотается
  (`console.warn`), никогда не пробрасывается наверх — уведомление в
  Telegram не должно уметь сломать создание/редактирование задачи или
  вопроса.
- Двусторонняя синхронизация ответов на вопросы через reply в Telegram
  держится на текстовом маркере `<code>Q:{id}</code>` внутри HTML-
  сообщения и парсинге `message.reply_to_message.text` регэкспом —
  без этого пришлось бы вести отдельную таблицу message_id↔questionId.
  Хрупко к ручному редактированию текста сообщения пользователем, но
  устойчиво к обычному use-case.
- Cron-роут дайджеста и вебхук защищены разными механизмами:
  `CRON_SECRET` как bearer-токен в `Authorization` (Vercel Cron сам его
  подставляет, если задан как env var), `TELEGRAM_WEBHOOK_SECRET` как
  заголовок `X-Telegram-Bot-Api-Secret-Token` (задаётся Telegram при
  регистрации вебхука через `setWebhook`). Обе проверки пропускаются,
  если соответствующий секрет не задан в env — удобно для локальной
  разработки, но значит секреты обязательны в проде.
- Один активный токен привязки на пользователя: генерация нового
  диплинка удаляет предыдущий неиспользованный токен этого же email.

## Ограничения / чего нет

- Нет настоящего realtime (WebSocket/Supabase Realtime) — только polling.
- Нет rate limiting на логин/регистрацию (риск брутфорса).
- Нет пагинации досок/задач — при тысячах задач на одной доске интерфейс
  начнёт тормозить (рендер, не база).
- Нет тестов (unit/e2e) и CI — только ручная/curl-проверка на каждом шаге.
- `board_members`/`Board.memberEmails` — легаси с ранних версий, фактически
  вытеснено участием в пространстве (`workspace_members`); можно почистить.
- Нет UI передачи владения доской/пространством — удаление владельца
  блокируется, но переназначить владельца через интерфейс нельзя.
- Физика мини-игр подобрана на глаз, не тестировалась строго.
- Telegram-уведомления ретраятся (до 3 попыток, экспоненциальный
  бэкофф/`retry_after`), но не через очередь — если все попытки в рамках
  одного serverless-вызова исчерпаны, уведомление в Telegram теряется
  (внутриприложенческое в колокольчике при этом всё равно создаётся —
  `notify()` пишет его первым, независимо от исхода отправки в Telegram).
- Колокольчик не чистит старые уведомления — таблица `notifications`
  растёт бессрочно, `listNotifications` просто берёт последние 30. Нет
  ограничения/архивации на бэкенде.
- Комментировать задачу может любой участник пространства (не только
  создатель/исполнитель) — сознательное решение ради простоты, как и с
  вопросами; если понадобится более узкая видимость — потребуется
  отдельная модель прав на уровне доски.

## Что осталось / могло бы понадобиться

- Пагинация/архивирование задач на больших досках.
- Realtime вместо polling, если 12-секундная задержка станет проблемой.
- Rate limiting на `/api/auth`, `/api/auth/register`.
- Очистка легаси board-level membership.
- Передача владения доской/пространством.
- Тесты, CI/CD пайплайн.
- Если объём скриншотов вырастет — перенос вложений из base64-в-Postgres
  в Vercel Blob/Supabase Storage.

## Деплой

```bash
npm install
npm run db:migrate      # после любого изменения schema.sql.ts (в т.ч. task_events/notifications/password_reset_tokens/telegram_links-колонок)
npm run dev              # локально
npx vercel --prod         # прод
npm run telegram:webhook  # один раз после деплоя/смены APP_URL/секрета/команд — регистрирует вебхук И команды (/setMyCommands) в Telegram
```

После этого захода обязательно `npm run db:migrate` перед первым
использованием на проде — добавились таблицы `task_events`,
`notifications`, `password_reset_tokens` и новые колонки в
`telegram_links` (`username`, `notify_*`, `digest_hour_utc`).

`.env.local`: `DATABASE_URL` (Transaction Pooler!), `SESSION_SECRET`
(`openssl rand -hex 32`). Плюс для Telegram-бота: `TELEGRAM_BOT_TOKEN`
(от @BotFather), `TELEGRAM_BOT_USERNAME` (без `@`), `TELEGRAM_WEBHOOK_SECRET`
(любая случайная строка, сверяется с заголовком от Telegram),
`APP_URL` (публичный HTTPS-адрес прода, нужен для диплинков и регистрации
вебхука — на Vercel можно не задавать, используется `VERCEL_URL`),
`CRON_SECRET` (bearer-секрет для `/api/cron/telegram-digest`). Те же
переменные — в Vercel → Environment Variables.

### Google Calendar

Опционально — без этих переменных виджет «Сегодня» просто показывает
заглушку «не настроен», остальное приложение работает как обычно.
Нужна таблица `google_calendar_links`, поэтому после добавления этой
фичи обязательно прогнать `npm run db:migrate` (см. выше), если ещё
не прогнано.

1. Google Cloud Console (console.cloud.google.com) → создать проект
   (или выбрать существующий).
2. «APIs & Services» → «Library» → найти **Google Calendar API** →
   Enable.
3. «APIs & Services» → «OAuth consent screen»: тип **External**,
   заполнить название приложения и email; добавить scope
   `.../auth/calendar.readonly`; на этапе Test users, пока приложение
   не прошло верификацию Google, добавить туда все email, которые
   будут подключать календарь (иначе Google откажет им в доступе).
4. «APIs & Services» → «Credentials» → «Create Credentials» → **OAuth
   client ID** → тип **Web application**.
5. В «Authorized redirect URIs» добавить:
   `<APP_URL>/api/google-calendar/callback`
   (например `https://team-task-tracker-delta.vercel.app/api/google-calendar/callback`;
   для локальной разработки — ещё и `http://localhost:3000/api/google-calendar/callback`).
6. Скопировать **Client ID** и **Client secret** → вписать в
   `.env.local` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) и в Vercel
   → Environment Variables → **Redeploy**, чтобы переменные подхватились.
